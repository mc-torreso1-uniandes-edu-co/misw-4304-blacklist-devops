# Entrega 2 · Pipeline de integración continua

Tarea 1.11 (#103) · Épica E2 · Implementación

Este documento registra la creación del pipeline de AWS CodePipeline que inicia el build de forma
automática con cada *push* a `main` y con cada *pull request*. Parte de las decisiones de las tareas 1.1 y
1.2 (#93 y #94), del diseño de `docs/ci/1.1-diseno-pipeline.md`, de los roles de 1.5 (#97), de la conexión
de 1.6 (#98) y del proyecto de CodeBuild de 1.7 (#99); no reemplaza el enunciado oficial de
`docs/entrega-2-integracion-continua.md`.

El pipeline se creó el **24 de octubre de 2026** (9:06, UTC-05:00) en la cuenta del proyecto y en la región
`us-east-2` (Ohio). La creación se hizo con la AWS CLI y el resultado se verificó con la misma CLI y en la
consola de AWS.

## 2. Disparadores

Un solo pipeline con dos disparadores de Git, definidos en la configuración del pipeline:

| Disparador | Eventos | Ramas de destino | Rutas excluidas |
|---|---|---|---|
| *Push* | Push | `main` | Ninguna |
| *Pull request* | Abierto (`OPEN`) y actualizado (`UPDATED`) | `dev` y `main` | `docs/**`, `postman/**`, `**/*.md` |

**Versión 2: se quitó la exclusión del *push* a `main` por el punto 4 de la rúbrica.** El enunciado pide que cada
commit en la rama principal inicie el build. Con la exclusión, una promoción de solo documentación no disparaba
nada. El pipeline se creó con las rutas excluidas también en el *push* (versión 1) y se actualizó a la versión 2
con los comandos de la sección 5.2. El disparador de *pull request* conserva las exclusiones.

La acción de origen tiene `DetectChanges` en `false`: la detección de cambios la hacen estos disparadores y no
una regla de EventBridge. Por eso la pestaña *Desencadenadores de EventBridge* de la consola aparece vacía.
Los filtros de Git se ven en la pantalla de edición del pipeline (sección 6).

## 3. Decisiones

| Aspecto | Decisión | Motivo |
|---|---|---|
| Tipo de pipeline | V2 | Es el único que admite filtros de *pull request* y de rutas (decisión de #93) |
| Modo de ejecución | `QUEUED` | Evita que la ejecución de un *pull request* reemplace a una de `main` en curso |
| Un solo pipeline | Con los dos disparadores | Un solo recurso que mostrar y mantener |
| Rutas excluidas | Solo en el *pull request*: documentación y colección de Postman | No cambian el código y cada ejecución consume minutos de construcción. El *push* a `main` no excluye nada, porque la rúbrica pide que cada commit en la rama principal inicie el build |
| Variable `COMMIT_ID` | En la acción de construcción | El origen llega al build sin la carpeta `.git`; el `buildspec.yml` la usa para la etiqueta del artefacto |
| Creación | AWS CLI | Es reproducible y queda el archivo de definición completo |

```bash

```

El comando solo debe ejecutarse si el pipeline no existe. La creación de recursos de AWS requiere
confirmación humana previa y no debe repetirse sobre el pipeline existente.

Esta ejecución **no** es la ejecución fallida que pide el documento de la entrega: esa debe fallar en la fase
de pruebas, por una prueba rota.

### 5.2 Versión 2: quitar la exclusión del *push*

Se ejecutó en AWS CloudShell. Primero se guarda la definición vigente en `p1.json`, que sirve para revertir; luego
se quita `filePaths` solo de los disparadores de *push* y se actualiza el pipeline:

```bash
aws codepipeline get-pipeline --name blacklist-devops-ci-pipeline --region us-east-2 --query pipeline > p1.json
jq '{pipeline: (.triggers[].gitConfiguration.push[] |= del(.filePaths))}' p1.json > p2.json
aws codepipeline update-pipeline --cli-input-json file://p2.json --region us-east-2
```

Verificación: el *push* debe salir sin `filePaths` y la versión debe ser 2.

```bash
aws codepipeline get-pipeline --name blacklist-devops-ci-pipeline --region us-east-2 \
  --query "pipeline.{version:version,triggers:triggers}"
```

Resultado: `"version": 2`, el disparador de *push* con solo `branches.includes: ["main"]` y el de *pull request*
con sus rutas excluidas. Antes de actualizar, `diff` entre `p1.json` y `p2.json` mostró que lo único que cambiaba
era el bloque `filePaths` del *push*.

Para revertir, se actualiza el pipeline con `p1.json` envuelto en `{"pipeline": ...}`.

### 5.3 Comprobación de la versión 2

El 27 de octubre de 2026 se fusionó en `main` la promoción #172, que creó el commit `3db0adb`. Ese commit solo
cambió archivos de `docs/`, rutas que la versión 1 excluía del *push*. Su *push* inició la ejecución `19089be6`
a las 18:50 (UTC-05:00), que terminó correctamente a las 18:51, en 1 minuto 8 segundos. Es la prueba de que
un commit de solo documentación en la rama principal inicia el build, que es lo que pide el punto 4 de la
rúbrica.

## 7. Notas

- **Dónde queda el artefacto.** El `buildspec.yml` declara `dist/app-*.zip` en la sección `artifacts`, que el
  pipeline entrega como `BuildArtifact`. CodePipeline lo guarda en su carpeta del bucket con un nombre
  generado, y el `app-<commit>.zip` queda dentro de ese objeto. El diseño proponía además copiarlo con
  `aws s3 cp` para dejarlo suelto en el bucket. Está pendiente decidirlo con el equipo y ajustar el diseño y
  este documento a lo que se elija.
- **Acción de origen.** `BranchName` es `main`; con los filtros de *pull request*, el pipeline usa el commit
  de la rama de origen del *pull request* (documentación de AWS), y con el *push*, el de la rama de destino.
- **Costo.** Las rutas de documentación están excluidas del disparador de *pull request* para no gastar minutos
  de construcción. El *push* a `main` no las excluye. El disparador de *pull request* se puede desactivar al
  terminar las capturas.
