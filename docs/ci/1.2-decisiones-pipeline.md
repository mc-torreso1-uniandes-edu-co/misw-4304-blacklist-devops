# Entrega 2 · Decisiones del pipeline de integración continua

Issue #94 · Épica E2 · Implementación

Este documento registra las decisiones del equipo sobre las pruebas, el artefacto, el build fallido y
los recursos de AWS para la Entrega 2. Complementa el diseño general del pipeline de #95 y no reemplaza
el enunciado oficial de `docs/entrega-2-integracion-continua.md`.

## 1. Decisiones heredadas de la tarea 1.1

Las siguientes decisiones quedaron cerradas en el issue #93 y se usan como base:

| Aspecto | Decisión | Motivo |
|---|---|---|
| Rama principal | `main` | Es la rama estable y por defecto del repositorio; equivale a `master` en el enunciado |
| Mecanismo | AWS CodePipeline V2 con etapas de origen y construcción | Permite centralizar el origen de GitHub y la ejecución de CodeBuild, y deja preparada la reutilización para la Entrega 3 |
| Ejecutor | AWS CodeBuild | Ejecuta las pruebas y genera el artefacto |
| Acceso a GitHub | Conexión de GitHub de AWS | No expone tokens personales ni llaves estáticas |
| Disparadores | *Push* a `main` y *pull requests* | Permite validar cambios antes de fusionarlos y construir la rama principal |
| Modo de ejecución | `QUEUED` | Evita que una ejecución de un *pull request* reemplace una ejecución de `main` que esté en curso |
| Región | `us-east-2` | Es la región fijada para el proyecto y el plan gratuito |

Las características avanzadas no se activarán. Esta condición se verificará en la consola al crear la
conexión y el pipeline.

## 2. Pruebas del build

### Decisión

CodeBuild ejecutará las pruebas con SQLite en memoria, usando `APP_ENV=testing` y `TestConfig`. No se
levantará PostgreSQL dentro del build.

### Motivos

- `app/config.py` ya configura `sqlite://` para el ambiente de pruebas.
- La suite es determinista y no depende de servicios externos.
- El build es más rápido y reproducible.
- No requiere `DATABASE_URL` ni otras credenciales.
- El enunciado permite ejecutar las pruebas sin un motor de base de datos.

La suite verificada antes de registrar esta decisión produjo **85 pruebas aprobadas** con `pytest -q`.

La base de datos PostgreSQL de RDS continúa siendo necesaria para la ejecución del microservicio en
Beanstalk y para la prueba funcional con Postman; no se usa dentro de las pruebas unitarias del build.

## 3. Artefacto

### Decisión

El pipeline generará un archivo ZIP y lo publicará en un bucket privado de Amazon S3. No se usará una
imagen de contenedor en esta entrega.

| Aspecto | Decisión |
|---|---|
| Región del bucket | `us-east-2` |
| Bucket | `blacklist-devops-ci-artifacts-253041091381` |
| Generador | `scripts/empaquetar.py` |
| Nombre | `app-<commit-corto>.zip` |
| Ejemplo | `app-a1b2c3d.zip` |
| Versión | El archivo `VERSION` contiene la misma etiqueta del artefacto |
| Destino | S3, sin despliegue automático |

La etiqueta se obtiene del commit que se está construyendo. El script ejecuta las pruebas antes de
crear el paquete; si una prueba falla, no genera el ZIP.

### Contenido esperado

El paquete contiene únicamente los archivos necesarios para ejecutar la aplicación en Elastic Beanstalk:

```text
application.py
app/
requirements.txt
Procfile
.ebextensions/
VERSION
```

No contiene:

```text
tests/
docs/
scripts/
.env
.venv/
instance/
archivos .db
secretos o tokens
```

Esta decisión conserva el procedimiento validado en la Entrega 1: `scripts/empaquetar.py` genera el
paquete, escribe `VERSION` y el despliegue posterior en Beanstalk es manual.

## 4. Build fallido

### Decisión

El build fallido se provocará en una rama temporal aislada y se ejecutará manualmente. La rama nunca se
fusionará con `main` ni con `dev`.

### Procedimiento

1. Crear la rama temporal `test/build-fallido`.
2. Agregar una prueba que falle intencionalmente.
3. Ejecutar manualmente CodeBuild con esa versión del código.
4. Verificar que el build termina en estado `Failed` durante la fase de pruebas.
5. Revisar los registros y guardar el mensaje del fallo.
6. Confirmar que no se genera un artefacto nuevo en S3.
7. Confirmar que `main` y `dev` no cambian.
8. Guardar las capturas y eliminar la rama temporal.

La rama de prueba no tendrá PR hacia `main` ni `dev`, y la prueba intencionalmente fallida no quedará en
ninguna rama protegida.

## 5. Recursos de AWS

Los nombres definidos para la configuración de la Entrega 2 son:

| Recurso | Nombre |
|---|---|
| Bucket S3 | `blacklist-devops-ci-artifacts-253041091381` |
| Proyecto CodeBuild | `blacklist-devops-ci-build` |
| Pipeline CodePipeline | `blacklist-devops-ci-pipeline` |
| Rol de CodeBuild | `blacklist-devops-codebuild-role` |
| Rol de CodePipeline | `blacklist-devops-codepipeline-role` |
| Conexión de GitHub | `blacklist-devops-github-connection` |

Los nombres no reemplazan ni chocan con los recursos de la Entrega 1, que conserva `blacklist-devops`,
`Blacklist-devops-env`, `blacklist-db`, `blacklist-eb-service-rol` y
`blacklist-ec2-instance-rol`.

## 6. Ventana de uso de Beanstalk y RDS

Beanstalk y RDS se encenderán únicamente durante las sesiones de configuración, pruebas, despliegue
manual, ejecución de Postman y grabación del video. Se apagarán inmediatamente después de terminar la
grabación y validar la evidencia.

El entorno `Blacklist-devops-env` y la RDS `blacklist-db` no forman parte del build de CI. El pipeline
solo genera el artefacto; la carga y el despliegue del ZIP en Beanstalk se harán manualmente, como exige
el alcance de esta entrega.

## 7. Evidencia pendiente

Estas decisiones se comprobarán con evidencia durante las tareas posteriores:

- Resultado de `pytest` y fase de pruebas de CodeBuild.
- Lista del contenido del ZIP y archivo `VERSION`.
- Hash del artefacto y objeto almacenado en S3.
- Capturas del bucket privado y su cifrado.
- Capturas del proyecto CodeBuild y del pipeline V2.
- Ejecución exitosa y ejecución fallida.
- Confirmación de que no se ejecuta ningún despliegue automático.
- Capturas sin tokens, contraseñas, `DATABASE_URL` ni `JWT_SECRET_KEY`.
