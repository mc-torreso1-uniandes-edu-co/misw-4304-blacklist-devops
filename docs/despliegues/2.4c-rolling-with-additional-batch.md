## 6. Hallazgos

- **Capacidad adicional:** AWS lanzó una instancia temporal, por lo que el máximo simultáneo fue de
  4 instancias. La instancia adicional fue `i-03d76ef45d72321de`.
- **Disponibilidad:** el monitor registró 891 respuestas HTTP 200 y ninguna respuesta no-200.
- **Convivencia de versiones:** `v3-rolling` y `v4-rollingbatch` convivieron durante 7 min 38 s,
  con 173 cambios de versión entre solicitudes consecutivas mientras el balanceador distribuía el
  tráfico entre instancias con versiones diferentes.
- **Tiempo:** el despliegue duró 9 min 19 s, mayor que Rolling porque creó, verificó y registró un
  lote adicional antes de completar la actualización.
- **Warning temporal:** después del despliegue, AWS mostró que 3 instancias online estaban por debajo
  del mínimo temporal de 4. El Auto Scaling Group volvió a `min=3`, `desired=3`, `max=6`; las 3
  instancias finales quedaron `InService / Healthy` y la salud volvió a `Ready / Green / Ok` a las
  11:54:27 UTC-5. Durante la actualización también hubo una transición a `Warning` a las 11:46:27
  porque el balanceador no marcó sana una de las cuatro instancias; volvió a `Info` a las 11:47:27.
- **Reemplazo:** la instancia adicional permaneció y AWS terminó `i-087c560a12e0ffa07` como excedente.
  Por ello, no quedaron exactamente los mismos IDs iniciales, aunque sí quedaron 3 instancias
  saludables al finalizar.
- **Costo:** hubo una instancia `t3.micro` adicional temporal; no se creó un entorno paralelo.
- **Cuándo conviene:** cuando se quiere conservar capacidad durante la actualización y se acepta
  un despliegue más largo y el costo temporal de una instancia adicional.
