## 3. Procedimiento

1. Copia limpia del repositorio, sin archivos locales:

   ```bash
   mkdir -p ci/src ci/deps
   git archive HEAD | tar -x -C ci/src
   ```

2. Fase de instalación, con red, en un entorno virtual nuevo:

   ```bash
   docker run --rm -v "$PWD/ci/src:/src:ro" -v "$PWD/ci/deps:/deps" -w /src python:3.13.16-slim \
     bash -c "python -m venv /deps/venv && /deps/venv/bin/pip install -r requirements-dev.txt"
   ```

3. Fase de pruebas, sin red, con las mismas variables del `buildspec.yml`:

   ```bash
   docker run --rm --network none -e APP_ENV=testing \
     -v "$PWD/ci/src:/src:ro" -v "$PWD/ci/deps:/deps:ro" python:3.13.16-slim bash -c '
       cp -r /src /work && cd /work && export PATH=/deps/venv/bin:$PATH
       python -m pytest -q --cov=app -rw
       for i in 1 2 3; do python -m pytest -q -p no:cacheprovider; done
       for f in tests/test_*.py; do python -m pytest -q -p no:cacheprovider $f; done
       python -m pytest -q -p no:cacheprovider $(ls tests/test_*.py | sort -r)'
   ```

## 4. Condiciones que el build debe mantener

- **No definir `DATABASE_URL`.** `TestConfig` usa SQLite en memoria solo cuando esa variable no existe. Si
  el proyecto de CodeBuild la definiera, las pruebas intentarían conectarse a ese motor.
- **No definir secretos.** Las pruebas firman los tokens con la clave fija de `TestConfig`; el build no
  necesita `JWT_SECRET_KEY`.
- **`APP_ENV=testing`**, como ya lo define el `buildspec.yml` de la tarea 1.8 (#100).
- **Instalar `requirements-dev.txt`**, que incluye `requirements.txt` y agrega `pytest` y `pytest-cov`.

## 5. Observación sobre Windows

En Windows, `pytest --cov=app` muestra la advertencia `CoverageWarning: Couldn't import C tracer`, porque
el control de aplicaciones del sistema bloquea la extensión compilada de `coverage`. La cobertura se mide
igual, con el trazador en Python, y la advertencia no aparece en Linux ni en el build.
